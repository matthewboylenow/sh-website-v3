Why this shape

Parish sites change weekly, not hourly. Data volumes are tiny (hundreds of events, dozens of ministries, one weekly bulletin). A custom backend over Postgres is simpler than a CMS, the admin UI can be purpose-built for the two or three people who use it, and nothing about this stack gets in the way of moving hosts if that ever becomes necessary.

02Database — Neon setup

Neon gives us Postgres with serverless pooling, auto-scaling to zero, and a branch per deploy — which means every PR preview gets its own isolated copy of the database. Production is untouched until the PR merges.

Project layout

  • One Neon project — sainthelen
  • Two roles — sainthelen_owner (migrations), sainthelen_app (runtime reads/writes, no schema access)
  • Three branches at minimum — main (prod), staging (the parish team's QA copy), and automatic preview branches per PR

Connection

Use Neon's serverless driver for Edge compatibility and the standard postgres driver for Node. Drizzle handles both — one config, two transports.

// db/index.ts
import { drizzle } from "drizzle-orm/neon-http";
import { neon } from "@neondatabase/serverless";
import * as schema from "./schema";

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
Branching pattern

Every PR gets a Neon branch cloned from main. The Vercel preview deploy reads from it. When the PR merges, migrations run once against main and the branch is deleted. Staff can QA from staging; engineers never touch production data.

Why blobAssets exists

Other tables reference assets by our key — not the blob URL. That means we can rotate the underlying CDN or migrate to a different file store later without a schema migration on seven tables. The indirection pays for itself the first time a URL format changes.

04Migrations & seeding

Drizzle Kit generates migrations from schema diffs and applies them in order. Seeds live alongside.

# Generate a migration after editing schema.ts
pnpm drizzle-kit generate

# Apply pending migrations to the current DATABASE_URL
pnpm drizzle-kit migrate

# Inspect / query during development
pnpm drizzle-kit studio

Seeding strategy

  • db/seed/site-settings.ts — inserts the singleton row with sensible defaults on first install.
  • db/seed/dev.ts — fixture data for local dev (5 events, 8 ministries, 4 staff, last 12 bulletins). Idempotent.
  • db/seed/prod-bootstrap.ts — runs once on launch day: imports Fr. Tom + clergy, last 52 bulletins from the 2.0 archive, and the weekly Mass schedule.
Migration discipline

Never edit a committed migration file. If something's wrong, write another migration that fixes it forward. This is the only way preview branches stay in sync with main.

Pattern — admin Route Handler

// app/api/admin/events/route.ts
import { NextResponse } from "next/server";
import { auth } from "@/auth";
import { db } from "@/db";
import { events } from "@/db/schema";
import { EventCreateSchema } from "@/lib/validators";
import { revalidateTag } from "next/cache";

export async function POST(req: Request) {
  const session = await auth();
  if (!session?.user || session.user.role === "ministry_lead")
    return NextResponse.json({ error: "forbidden" }, { status: 403 });

  const parsed = EventCreateSchema.safeParse(await req.json());
  if (!parsed.success)
    return NextResponse.json({ error: parsed.error.flatten() }, { status: 400 });

  const [row] = await db.insert(events).values({ ...parsed.data, createdBy: session.user.id }).returning();
  revalidateTag("events");
  return NextResponse.json(row, { status: 201 });
}

Editor UX choices worth calling out

One form per type. No nested schemas, no sanity-style references UI. Where relationships exist (event → venue, ministry → lead staff), we use a typeahead that hits /api/admin/staff?q=…. Draft by default. New rows start in draft; publishing is explicit. Inline uploads. The photo slot is a client-upload that goes straight to Blob; the row in blobAssets is created on completion and the editor stays on the page.

07Auth, roles & ministry self-service

Auth.js with two parallel sign-in methods: magic-link email (Resend) and SMS one-time-code (Twilio Verify). No passwords. Sign-in screen offers two tabs — "Email me a link" or "Text me a code." Either lands the user with a 30-day session cookie. Same session model, same role checks, same audit trail.

Day-1 admin

Seed file inserts a single user on first deploy: mboyle@sainthelen.org, role admin, also with phone set so SMS works from day one. From there, additional users are invited through /admin/users — no migration needed.

Sign-in flow

  1. User goes to /admin, gets redirected to /sign-in (no session).
  2. Picks Email link or Text me a code.
    • Email: Auth.js emits a verification token, Resend delivers the link, user clicks → session created.
    • SMS: server calls Twilio Verify verifications.create({ to, channel: 'sms' }), Twilio sends the 6-digit code, user enters it on the sign-in page, server calls verificationChecks.create({ to, code }) → session created.
  3. Either path lands at /admin with the same cookie. Sessions last 30 days; sliding refresh on activity.
  4. Sign-out clears the cookie. "Sign me out everywhere" rotates the user's session version, invalidating all active sessions in one click.

The user record gains two columns to support this: phone (E.164 format, unique, nullable) and preferredAuthMethod ('email' | 'sms', defaults to email). Twilio Verify handles its own rate-limiting; we add a per-user-per-hour cap on top to prevent SMS bill abuse if credentials leak.

User self-service

From /admin/account, any signed-in user can: update their name, change or add a phone number, switch their preferred auth method, and trigger "sign me out everywhere." Admins additionally see /admin/users for inviting, role-changing, deactivating, and reactivating others. There's no password reset flow because there are no passwords — if someone loses access to both email and phone, an admin re-issues their account.

Ministry self-service — draft & approve workflow

Built but disabled at launch. Code ships in the v1 release; the feature flag ENABLE_MINISTRY_SELF_SERVICE stays false until post-launch. Once flipped, ministry leads can be invited per-ministry as a controlled rollout.

The flow

  1. Admin invites leader@example.com with role ministry_lead + ministryId set to e.g. "Knights of Columbus."
  2. Lead signs in, lands at /admin, sees only their ministry edit page — no list of others, no events, no bulletins, no settings. Single-purpose view.
  3. Lead edits one or more fields (Option A model below). Changes go into a ministryEdits row keyed to that ministry, status pending.
  4. Admin gets a notification — email + a badge in the admin shell ("3 pending edits"). Opens /admin/approvals, sees a queue of pending edits with a diff view (current value vs. proposed, side-by-side per field).
  5. Admin clicks Approve → changes apply to ministries, revalidateTag("ministries") fires, edit row is archived. Or Reject with a note → edit row goes back to lead with the reason.

Why "controlled blocks," not free-form

Ministry leads cannot break the layout. They cannot add or reorder anything. They edit a fixed set of fields with constrained inputs:

That's it for v1. No rich text editor with arbitrary HTML, no custom CSS, no drag-and-drop sections, no embedded videos, no ability to add or remove fields. Every approved ministry page renders to the same template. This is what "very controlled" looks like in practice.

Block editor v2 — deferred to §15

If, post-launch, parish staff want a more flexible editor (add a custom section, reorder, embed something), that's the v2 conversation. Field-based v1 is deliberately rigid so the first six months of self-service produce consistent, on-brand pages every time.

08File storage — Vercel Blob + custom CDN

Uploads go to Vercel Blob directly from the admin UI (client upload token, no server round-trip for the bytes). The stored blob URL is rewritten through cdn.sainthelen.org so every public-facing asset carries the parish domain.

Upload flow

  1. Editor drops a photo into the event editor.
  2. Client calls /api/admin/upload — server validates role, returns a Vercel Blob client-upload token scoped to a path like events/<uuid>/<filename>.
  3. Browser uploads bytes directly to Blob storage using that token.
  4. On success, client calls back to /api/admin/upload/complete with the returned url, size, mime. Server:
    • Runs sharp to read dimensions and generate a WebP derivative for the event hero size.
    • Inserts a row in blobAssets with a stable key (e.g. evt_harvest-fest-2026_hero).
    • Returns the key; client writes it into events.photoBlobKey.

Custom domain

Vercel Blob URLs look like https://xxx.public.blob.vercel-storage.com/…. We front them with a Vercel rewrite so assets are served from cdn.sainthelen.org instead.

// next.config.ts
export default {
  async rewrites() {
    return [
      {
        source: "/cdn/:path*",
        destination: "https://<blob-store-id>.public.blob.vercel-storage.com/:path*",
      },
    ];
  },
};

Then DNS: cdn.sainthelen.org → CNAME to the Vercel app, and the rewrite maps anything under /cdn/* to the Blob origin. The app's asset helper translates a blobAssets.key to https://cdn.sainthelen.org/cdn/<path>.

Why custom domain matters

Photos and bulletins shared on social media, forwarded in email, or scraped into Google's image index will all carry the sainthelen.org origin. That's brand hygiene and SEO. The abstraction also means we can swap Blob for S3 or Cloudflare R2 in the future by editing one rewrite — no content URLs change.

Image delivery

  • All public-site images render via next/image. images.remotePatterns whitelists cdn.sainthelen.org.
  • We upload one source file; Next generates sized WebP variants at request time and caches them on the edge.
  • The design system already ships placeholder components, so an event without a photo still renders cleanly.

09Cache, revalidation, ISR

RSC fetches the DB directly. We layer Next's fetch cache on top with tags so admin mutations can revalidate precisely.

Tags in use

  • events — invalidated on any event publish / unpublish / delete.
  • events:<slug> — scoped to the detail page.
  • ministries, mass-times, staff, bulletins, seasonal, site-settings — same pattern.
// In a Server Component that reads events:
import { unstable_cache } as cache } from "next/cache";

const getPublishedEvents = cache(
  async () => db.select().from(events).where(eq(events.status, "published")),
  ["events:published"],
  { tags: ["events"], revalidate: 3600 } // 1hr fallback
);

Admin mutations call revalidateTag("events") (or more specific tags). The public site re-renders on the next request. No webhook round-trip, no external service.

11Integrations — Touchpoint, Fathom, Resend, Twilio

Everything external the site talks to. Four integrations, all simple, all replaceable.

Touchpoint giving (donations)

The Give page does not process payments. Every CTA outbound-links to Touchpoint, the parish's giving platform. URLs are stored in siteSettings and editable from /admin/settings/giving so seasonal links can be rotated without a deploy.

// db/schema.ts — add to siteSettings (singleton row)
giving: jsonb("giving").$type<{

The Give page Server Component reads siteSettings.giving, renders the primary CTA + designation list, and surfaces any active seasonal campaigns whose date window includes today. Admin UI at /admin/settings/giving is a single form: primary URL, recurring URL, a repeatable list of designations, and a repeatable list of seasonal campaigns with date pickers. No deploy needed to add Christmas, Easter, Mother's Day, building fund pushes, or anything else.

Why outbound, not embedded

Embedding Touchpoint's checkout would put us in PCI scope, force us to handle recurring billing edge cases, and require a rebuild every time Touchpoint changes their flow. Outbound link is the right call: ~one click of friction, zero compliance burden, zero ongoing maintenance, and Touchpoint already handles tax receipts. If Touchpoint is ever replaced (different ChMS, different processor), it's a settings edit — no code change.

Twilio Verify (SMS sign-in)

One-time codes only — we never store phone numbers as a sole identifier; the users.phone field is the link. Verify handles code generation, retry windows, and per-number rate-limits server-side. We add a per-user-per-hour app-level cap on top.

// lib/auth/sms.ts
import twilio from "twilio";

const client = twilio(process.env.TWILIO_ACCOUNT_SID!, process.env.TWILIO_AUTH_TOKEN!);
const verifySid = process.env.TWILIO_VERIFY_SERVICE_SID!;

export async function sendCode(phone: string) {
  return client.verify.v2.services(verifySid)
    .verifications.create({ to: phone, channel: "sms" });
}

export async function checkCode(phone: string, code: string) {
  const result = await client.verify.v2.services(verifySid)
    .verificationChecks.create({ to: phone, code });
  return result.status === "approved";
}

Cost per sign-in: ~$0.05 USD (Verify fee + SMS) in the US. With 3–8 admins signing in a few times a week, this is well under $5/month. Twilio bills monthly; first month free up to a small quota.

12Backup strategy

Three layers, defense in depth. Each layer protects against a different failure mode. Combined cost: under $2/month.

LayerWhereRetentionRecovers from
1. Neon point-in-time recoveryNeon (built-in)7 days (free) / 30 days (paid)Accidental delete, bad migration, ransomware in the last week
2. Weekly pg_dump on Vercel CronVercel Blob12 weeks rollingNeon outage, account compromise, audit/restore-to-staging
3. Monthly off-platform snapshotBackblaze B2 (cheap S3-compatible)Indefinite (≈$0.005/GB/mo)Vercel + Neon both unrecoverable, vendor lock-out, multi-year audit

Layer 2 — Weekly Vercel Cron

// app/api/cron/backup/route.ts
import { spawn } from "node:child_process";
import { put, list, del } from "@vercel/blob";

export const runtime = "nodejs";
export const maxDuration = 300;  // 5 min — adjust for DB size

export async function GET(req: Request) {
  if (req.headers.get("authorization") !== `Bearer ${process.env.BACKUP_CRON_SECRET}`) {
    return new Response("unauthorized", { status: 401 });
  }
  const stamp = new Date().toISOString().slice(0, 10);
  const child = spawn("pg_dump", [process.env.DATABASE_URL_OWNER!, "--no-owner", "--clean"], { stdio: ["ignore", "pipe", "pipe"] });
  const blob = await put(`backups/sainthelen-${stamp}.sql`, child.stdout, { access: "public", contentType: "application/sql" });

  // Prune anything older than 12 weeks
  const { blobs } = await list({ prefix: "backups/" });
  const cutoff = Date.now() - 84 * 24 * 60 * 60 * 1000;
  await Promise.all(blobs.filter(b => new Date(b.uploadedAt).getTime() < cutoff).map(b => del(b.url)));

  return Response.json({ ok: true, url: blob.url });
}
// vercel.json
{
  "crons": [
    { "path": "/api/cron/backup", "schedule": "0 7 * * 0" }
  ]
}

Sundays at 07:00 UTC (after the early Mass rush, before any office hours). Vercel Cron pings the route, the route streams pg_dump output straight into Blob, prunes anything older than 12 weeks. Backup history is then visible in /admin/backups with a one-click "download" or "restore to staging" affordance.

Layer 3 — Monthly off-Vercel snapshot

The first cron run of each month also pushes the dump to Backblaze B2 (S3-compatible, ~$6/TB/mo, free egress to Cloudflare). This is your insurance against "Vercel + Neon are simultaneously unrecoverable" — vanishingly unlikely, but trivially cheap to protect against. Same dump, aws s3 cp with B2 endpoint env vars, retention is forever (the storage cost is negligible at this DB size — pennies per year).

Restore drill

Once a quarter, an admin runs the documented restore drill: pick a backup, restore it to a Neon branch, point staging at the branch, verify content. Documented as a checklist in docs/runbooks/restore.md. The first drill happens before launch as part of go-live readiness.

A backup you've never restored is not a backup

Layer 1 means little if no one's ever clicked "recover." The pre-launch restore drill turns this from theory into a known-good muscle. Schedule it.

13Accessibility — WCAG 2.2 AA + custom widget

The pledge

The site passes WCAG 2.2 Level AA without the widget. The widget is a comfort layer for users who want overrides on top of an already-compliant baseline — it is not a substitute for compliance. Snake-oil overlay vendors (you know the names) have been litigated repeatedly precisely because they market themselves as compliance. We're not doing that.

Baseline WCAG 2.2 AA work (every page)

  • Color contrast ≥ 4.5:1 for body text, ≥ 3:1 for large text and UI controls. Tokens in the design system are pre-checked.
  • Every interactive element is reachable by keyboard, in source order, with a visible focus ring (rust-yellow 2px outline + offset).
  • Skip-to-content link as the first focusable element on every page.
  • Forms: every input has a visible label (no placeholder-as-label), errors are announced via aria-live, inline + summary at top of form.
  • Images have meaningful alt; decorative images use alt="". Admin UI requires alt text on photo upload before save.
  • Headings follow document outline. One h1 per page, no skipped levels.
  • prefers-reduced-motion respected by default — animations disable, transitions shorten.
  • Pages remain usable at 200% zoom and 320 px viewport width.
  • Mass-times widget, events list, and ministry cards all expose semantic landmarks (main, nav, article, aside).
  • Automated CI: axe-core runs on the home + 3 interior pages on every PR. Build fails on any new violation.

The widget — what it actually does

Floating button bottom-left (not bottom-right — that's reserved for the Give FAB). Opens a small panel with five controls. State persists in localStorage as sh.a11y.v1; applied via data-* attributes on <html> so CSS can hook them.

ControlEffectHow
Text sizeThree steps: small / default / large (90% / 100% / 115%)Sets --font-scale CSS variable; type tokens already use it
High contrastSwaps to higher-separation palettedata-contrast="high" on html; ~20 lines of CSS overrides token values
Reduce motionDisables non-essential animation regardless of OS settingdata-motion="reduce"; CSS targets html[data-motion="reduce"] *
Dyslexia-friendly fontBody text switches to OpenDyslexicdata-font="dyslexic"; OpenDyslexic loaded only when toggled
ResetClears all overridesRemoves the localStorage key and data-* attrs

What the widget deliberately does not do

  • No "screen reader mode" — real screen readers don't need a website's permission.
  • No "epilepsy-safe profile" — the underlying site already has no flashing content; you can't toggle that from the page.
  • No "cognitive disability profile" — a panel can't simplify content; thoughtful copy and layout do that, baked in.
  • No big-cursor toggle, no link-highlight toggle, no spacing slider with 30 steps. Five controls, well-chosen, well-labeled.

The widget code lives in components/a11y-widget.tsx. It's gated by the ENABLE_A11Y_WIDGET flag so it can be turned off if the design changes. ARIA: the toggle button is a button with aria-expanded, the panel is role="dialog" with aria-modal="true" and a labeled close, focus is trapped while open, Escape closes.

Pre-launch: a11y audit by an independent reviewer (NV Access or a local consultant) plus user-testing with at least one keyboard-only user and one screen-reader user. Findings tracked as launch blockers.

14Staging environment — staging.sainthelen.org

A persistent staging environment for content review and pre-launch UAT, completely isolated from production. Lives until prod DNS flips, then sticks around as the QA target for future changes.

Setup

  1. Git: dedicated staging branch on the repo; protected, only fast-forward merges from main.
  2. Vercel: the same project deploys staging branch to staging.sainthelen.org automatically. Production deploys only from main.
  3. Database: dedicated Neon branch named staging — independent data, copy-from-prod once at setup, then evolves separately.
  4. Blob: separate Vercel Blob store; staging uploads never pollute production assets.
  5. Email sender: EMAIL_FROM="Saint Helen STAGING <staging@sainthelen.org>" so any test email is unmistakable.
  6. Twilio: separate Verify service so test sign-ins don't share rate-limits with prod.
  7. Fathom: not loaded — analytics stay clean.
  8. Robots: X-Robots-Tag: noindex via middleware on staging.sainthelen.org; Google never indexes it.
  9. Access control: Vercel deployment-protection password on the staging deployment. Public can't reach it; staff use a shared password kept in 1Password.

Who uses it

  • Pre-launch: Fr. Tom, comms lead, and ministry leaders review the site here before DNS flip. Photo placeholders get replaced. Copy gets edited inline. Mass times get verified.
  • Post-launch: any non-trivial change (new template, schema change, integration tweak) ships to staging first, gets approved, then promotes to main.
  • Sunday morning safety: never deploy to prod on Sundays. Staging is where weekend hot-fixes land for Monday review.
