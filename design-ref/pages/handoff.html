01Target stack & why

The mockup is built with hand-rolled HTML + CSS so it's portable — but it was designed against this stack. Every component has a natural landing spot here.

Framework
Next.js 15 (App Router)

RSC by default; "use client" only for interactive islands (filters, day picker, matchmaker quiz, bulletin modal).

Styling
Tailwind CSS 3.4+

Token-driven. Our CSS variables from colors_and_type.css translate cleanly into tailwind.config.ts.

Components
shadcn/ui

Use Dialog, Popover, Sheet, Tabs, Form. Restyle rather than replace — the kit already matches our radius + shadow scale.

Database
Neon Postgres + Drizzle

Custom backend — no external CMS. Parish staff edit content at /admin routes inside the same Next.js app. Full schema in the Backend Architecture doc.

Files
Vercel Blob

Photos and bulletin PDFs uploaded directly from the admin UI. Served through cdn.sainthelen.org so assets carry the parish domain.

Auth
Auth.js · magic links

Email magic-link sign-in via Resend. Three roles: admin, editor, ministry_lead.

Forms
React Hook Form + Zod

Welcome form, prayer requests, sacrament requests. Submit to a Route Handler; relay to parish CRM.

Hosting
Vercel

Preview deploys per PR, ISR for bulletin/events, Edge runtime for the /api/readings proxy.

Why custom backend, not a hosted CMS?

This site has tiny data volumes (dozens of ministries, weekly bulletin, a handful of events per month) and 3–8 total editors. A custom /admin UI over Postgres is simpler than a CMS, purpose-built for parish workflows, and eliminates vendor lock-in and monthly fees. Full architecture — schema, API, admin wireframes, upload flow — in the Backend doc.

06Content model

Seven tables in Postgres cover the entire site: events, massTimes, ministries, staff, bulletins, seasonalBanners, siteSettings — plus users / Auth.js tables and a blobAssets registry.

Full schema lives in the Backend doc

The complete Drizzle schema (every column, every type, every relationship), migration workflow, seed strategy, and API route map are documented separately in Backend Architecture →. That doc is the source of truth for anything database-shaped.

Query pattern

Public reads happen in Server Components via direct Drizzle queries — no API layer, no GraphQL, no codegen. Wrap each query in unstable_cache with a tag so admin mutations can revalidate precisely (see Backend doc §09). Co-locate queries with the component that consumes them (e.g. EventCard.query.ts). Avoid a central queries.ts — it becomes a tar pit.

07Interactive behaviors — contracts

The non-obvious pieces. What they do, how they should behave once in React.

Mega-menu

  • Opens on hover (desktop) and click (keyboard / touch). 140ms open delay, 220ms close delay to avoid flicker.
  • Escape closes. Tab cycles through visible links. First link in the opened panel gets focus on keyboard activation.
  • On mobile (< 900 px) the whole thing collapses into a Sheet.

Day picker (Mass page)

  • Default-selects today in the user's local timezone.
  • Arrow keys ←/→ move between days. Enter opens the day's schedule.
  • If the selected day is a Sunday with an active livestream, a Live now chip appears on the first matching Mass card.

Events filters

  • Filter state syncs to URL (?audience=families&category=worship) so links are shareable.
  • Search is fuzzy (uses fuse.js client-side). Trigger on / from anywhere on the page.
  • "My picks" saves selected events to localStorage. Clears on explicit reset.

Ministry matchmaker

  • Three questions → tag weights → top-5 ministries sorted by match score.
  • Scoring is client-side but the manifest comes from /api/matchmaker (cached, returns top-5). Keeps weights server-authoritative so comms can tune matches without a deploy.
  • Results page includes "email me these" — hits the welcome form endpoint with ministry IDs attached.

Bulletin modal

  • shadcn Dialog. Fullscreen on mobile. PDF viewer is a native <iframe> with a download fallback link.
  • Opens with the bulletin slug in the URL hash for deep-linking.

Give FAB

  • Only appears on viewports below 760 px and only after 400 px of scroll. Dismissible; remembers state per session (sessionStorage).
  • Never shown on the Give page itself.

08Accessibility & SEO

Accessibility — what we've already baked in

  • Focus ring uses rust on a 3 px offset. Visible on both cream and white.
  • Rust-on-white body text is blocked — we use --sh-rust-dark (6.1:1) instead.
  • All buttons are real <button> elements, not divs. Links carry discernible text.
  • Day picker and filter chips expose role="tablist" / role="tab"; arrow-key nav; aria-selected.

SEO — priorities

  • Mass times page needs a Schema.org Event block per Mass. This is how Google surfaces Mass times in the local box.
  • Events get Event schema with offers for registration-required items.
  • Organization schema on every page via the root layout — address, geo, sameAs (Facebook, YouTube, Instagram).
  • Sitemap generated from the database at request time. Revalidated on publish via tag.
